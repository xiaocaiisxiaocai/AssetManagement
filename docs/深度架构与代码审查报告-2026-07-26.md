## 一、总体印象

在深入阅读代码之前需要先说明：这是一个**完成度较高、工程素养不错**的项目——领域层与基础设施层分离干净（Domain 层未泄漏 EF Core / ASP.NET 细节）、审批流转普遍使用了 RowVersion 乐观并发、编号生成有专门的原子自增序列表设计、前端有相对完善的请求令牌防竞态机制（`createLatestRequestGuard`）、CLAUDE.md 记录了详尽的架构与编码约定。多数发现的问题不是"错误"而是"权衡/遗留/不一致"，这也是为什么下面很多问题的严重程度标注为 medium/low。

但也确实存在 **2 个 Critical 级别的部署缺陷会导致按官方文档操作必然失败**，以及 **2 个 High 级别的问题**需要尽快修复。此外，最突出的架构性主题是：**`WorkflowService`（资产审批）与 `MaterialFlowService`（料件流转）之间存在约 600+ 行结构相同的 BPMN 编排代码被复制而非复用**，这是本项目最值得投入重构精力的地方。

## 二、🔴 Critical / 🟠 High：需要优先处理

### 1. 【Critical】CI 工作流未提供 MySQL 服务，后端测试从未真正跑通过
**位置**：`.github/workflows/ci.yml:10-23`

backend job 直接在 `ubuntu-latest` 上执行 `dotnet test`，但没有任何 `services:` 段启动 MySQL 容器，也没有设置 `ASSETMGMT_TEST_MYSQL_PASSWORD`。而后端 39+ 个测试文件（`MySqlFixtureBase.cs`、`TestWebAppFactory.cs` 等）在拿不到该环境变量时会直接抛异常终止。也就是说，CI 中标注为"测试通过"的绿色勾从未真正验证过后端 500+ 项测试，质量门禁形同虚设。

**建议**：在 backend job 增加 `services: mysql: image: mysql:5.7`（配置 `MYSQL_ROOT_PASSWORD` 与健康检查），并通过 `env` 把同一密码传给 `dotnet test` 步骤；修复后应实际跑一次 CI 确认全部测试真正通过。

### 2. 【Critical】Docker Compose 部署文档与生产启动守卫逻辑自相矛盾，首次启动必然崩溃
**位置**：`deploy/docker/docker-compose.yml:31-43`、`deploy/docker/README.md`、`backend/src/AssetManagement.Api/Program.cs:251-257`

`deploy/docker/README.md` 宣称"首次启动"即可用默认账号 `1001/123456` 登录，但 `docker-compose.yml` 与 `.env.example` 均未设置 `ASSET_ADMIN_PASSWORD`。而 `Program.cs` 在生产环境 + 空库自动播种时，若该变量未配置会直接抛异常导致容器崩溃、`restart: always` 无限重启循环。按文档操作的用户会在首次部署时遇到无法解释的崩溃循环。

**建议**：在 `docker-compose.yml` 的 `api.environment` 中补充 `ASSET_ADMIN_PASSWORD: ${ASSET_ADMIN_PASSWORD}`，在 `.env.example` 中补充说明，并同步修正 README 的表述。

### 3. 【High】后端 Docker 镜像缺少 mysqldump，数据库备份功能在容器化部署下必然静默失败
**位置**：`deploy/docker/backend.Dockerfile:11-18`、`DatabaseBackupService.cs:52-76`

运行时镜像基于 `mcr.microsoft.com/dotnet/aspnet:8.0`，未安装 `mysql-client`。每日午夜的自动备份任务会持续失败但只记录日志，管理员很难察觉，直到真正需要恢复数据时才发现从未产生过可用备份——这是最容易被忽视、后果却最严重的一类问题。

**建议**：在 Dockerfile 运行时阶段增加 `apt-get install -y default-mysql-client`，并在部署验证流程中加入一次"立即备份"的冒烟测试。

### 4. 【High】BpmnEngine 抛出的 `InvalidOperationException` 未被业务层转换，会作为无意义的 500 错误返回
**位置**：`backend/src/AssetManagement.Domain/Workflow/BpmnEngine.cs`（多处）、`WorkflowService.cs`、`MaterialFlowService.cs` 的对应调用点

`BpmnEngine` 在遇到非法流程状态（节点无活跃 Token、审批人不在会签名单、排他网关无匹配分支等）时统一抛 `InvalidOperationException`，但调用方从未捕获并转换为 `BizException`。`ExceptionMiddleware` 只特殊处理 `BizException`，其余异常一律返回无上下文的 500。流程配置错误时用户看到的是"服务器内部错误"而非可读的业务提示，运维必须翻日志才能定位。

**建议**：在 `WorkflowService`/`MaterialFlowService` 调用 BPMN 引擎的地方捕获该异常并转换为语义化的 `BizException`（附带引擎原始 message）。

## 三、🏗️ 架构与设计问题

### 3.1 最值得优先重构：审批工作流与料件流转的编排逻辑被逐行复制（medium，出现在两个独立维度的审查中，属于全项目最突出的架构问题）
**位置**：`WorkflowService.cs`（`NormalizeSignStatesAsync`/`ReconcileInactiveSignersAsync`/`EnsureCurrentApproversResolvableAsync`/`ApprovalIdentity`/`ResolveApproverUserIdsAsync` 等）与 `MaterialFlowService.cs` 中约 600+ 行几乎逐字对应的实现（代码注释里作者自己也承认"逻辑与 WorkflowService.IsApproverForNode 对应，保持同步更新"）

`ApprovalFlow`（资产审批）与 `MaterialFlow`（料件流转）虽是两个领域实体，但都实现同一个 `IBpmnFlowInstance` 接口、驱动同一个 `BpmnEngine`，围绕它们的会签归一化、失效签核清理、审批人解析等 Infrastructure 编排代码被复制而非复用。这直接导致**功能矩阵已经不一致**：`WorkflowService` 支持加签/取消加签/转签，`MaterialFlowService` 完全没有对应能力（`IMaterialFlowService` 接口里根本没有这些方法）——这不是假设性风险，是已经发生的真实后果。任何审批规则变更都需要人工同步两处，一旦遗漏就会导致资产审批和料件审批行为不一致的 bug。

**建议**：抽取一个基于 `IBpmnFlowInstance` 接口编程的通用编排服务（如 `IBpmnApprovalResolver` / `BpmnFlowOrchestrator<TFlow>`），把只依赖接口成员的逻辑下沉为共享实现，两个 Service 只保留各自实体特有的业务副作用（改 Asset 状态 vs 改 TestMaterial 状态）；同时评估是否需要为 `MaterialFlow` 补齐加签能力以保持产品行为一致。

### 3.2 领域实体普遍贫血，状态机约束完全外置（low）
**位置**：`backend/src/AssetManagement.Domain/Entities/*.cs`

`Asset`、`ApprovalFlow`、`MaterialFlow` 等实体都是纯 DTO 风格：只有可变的 `get; set;` 属性，没有构造函数校验、没有状态迁移方法。真正的业务规则（"借用中资产不能再借用""保管人不能是自己"）全部写在 `Infrastructure` 层的 `WorkflowService`/`BizEffectApplier` 里。领域层没有基础设施泄漏这点是优点，但作为 DDD 实践看，实体退化为数据容器，不变式保护完全依赖调用方自觉，容易在多入口场景下遗漏校验。**非阻塞性问题**，`BpmnEngine` 本身作为"纯函数引擎 + 接口解耦"的设计反而是本仓库职责边界最清晰的部分，值得保留。

### 3.3 转签（TransferSign）功能前后端状态不一致，名存实亡
**位置**：`WorkflowService.cs:825-826`（恒抛异常拒绝）、`ApprovalController.cs:90-93`（路由仍暴露）、`DbSeeder.cs`（权限仍授予 supervisor 角色）、前端无任何转签 UI

Controller 路由、权限码 `approval:transfer-sign` 都存在且被种子数据授予角色，但服务层直接拒绝任何调用，前端也完全没有入口。功能处于"看起来存在但完全不可用"的半成品状态，容易在排查"审批人离职后如何转交审批"这类真实生产问题时造成混乱。

**建议**：二选一——彻底清理转签相关的路由/权限/前端痕迹，或真正实现 Token 迁移逻辑并补齐前端入口。

### 3.4 `web-antd`、`web-naive` 是完全未使用的重复脚手架，长期占用维护面
**位置**：`web/apps/web-antd`、`web/apps/web-naive`

CLAUDE.md 已明确声明这两个 app 不使用，但仍完整保留在仓库中（各 60+ 文件）并被 `pnpm-workspace.yaml` 纳入 monorepo，`src/api/core/menu.ts` 还指向 mock 后端接口，与真实后端契约完全不符。每次 `pnpm install`/`pnpm check` 仍会处理这两个包，增加认知负担和构建时间。

**建议**：物理删除，或迁移到 `templates/` 目录并从 `pnpm-workspace.yaml` 排除。

### 3.5 权限校验口径分散：控制器硬编码权限白名单 / 仅 `[Authorize]` 未声明权限码 / 前端硬编码后端应下发的权限元数据（3 条同类问题合并）
- `UserController.Options`（`UserController.cs:31-60`）在方法体内硬编码 12 个权限码的白名单数组，而非用项目自身约定的 `[HasPermission]` 声明式鉴权
- `TestMaterialController`/`TestProjectController` 部分接口仅用宽松的 `[Authorize]`，把细粒度授权完全下放到 Service 层，导致权限矩阵审计无法覆盖这批接口
- 前端 `routes/index.ts` 的 `hiddenAuthenticatedRoutes` 硬编码了 `material-flow:approve/view` 权限码，绕开了后端动态菜单下发机制；`admin/roles/permission-groups.ts` 的"菜单-权限"映射也是前端手工维护表，后端新增菜单时容易漏配

这三处的共同本质是：**项目自身约定"权限由后端统一下发"，但存在多处例外**，是权限口径长期漂移的隐患来源，虽不直接导致越权（后端仍有兜底），但会增加维护成本和未来引入越权 bug 的概率。

## 五、🔒 安全问题

1. **密码策略强度不足**（medium）：`PasswordPolicy.EnsureStrong` 只校验长度 6-12 位，无复杂度要求、无弱密码黑名单，配合系统默认密码固定为 `123456`（`AppConstants.cs:39`），存在长期低速撞库风险。（`Common/PasswordPolicy.cs:5-11`）
2. **JWT 以 localStorage 持久化 + 滑动续期放大 XSS 危害窗口**（medium）：`pinia-plugin-persistedstate` 把 `accessToken` 存入 `localStorage`（对 XSS 不设防），后端 `SlidingTokenMiddleware` 只要 token 剩余寿命不足一半就自动续期，实际上使 token 有效期趋近无限，一旦发生 XSS/token 泄露影响被显著放大。（`web/packages/stores/src/setup.ts:19-29`、`SlidingTokenMiddleware.cs`）
3. **后端未设置任何安全响应头**（medium）：全仓库未见 `Content-Security-Policy`/`X-Frame-Options`/`X-Content-Type-Options` 等中间件，在 token 走 localStorage 的前提下缺少 CSP 会使 XSS 危害不受限制。（`Program.cs`）
4. **Docker 部署路径未提供 TLS 终止**（medium）：`nginx.conf` 仅监听 80 端口，`docker/README.md` 全文未提 HTTPS 要求，与 IIS 部署路径明确要求 HTTPS 证书的安全基线不一致，JWT/密码可能明文传输。（`deploy/docker/nginx.conf:1-19`）
5. 修改密码 / 重置密码接口未做速率限制，仅登录接口受保护，理论上可对已登录用户做旧密码枚举（low）。（`AuthController.cs:40-46`）
6. CORS 配置本身安全（未开 `AllowCredentials`），但未对 `Cors:AllowedOrigins` 做合法性校验，完全依赖运维正确配置，配合 `WithExposedHeaders("accesstoken")` 若误配宽泛来源会导致 token 可被跨域读取（low）。（`Program.cs:230-236`）
7. 登录失败计数/限流状态保存在进程内存，不支持多实例横向扩展或滚动发布（发布后计数清零、攻击者可利用窗口期继续爆破），当前单实例部署下影响很小（low）。
8. appsettings 未显式配置 Kestrel `MaxRequestBodySize`/`FormOptions.MultipartBodyLengthLimit`，文件上传依赖应用层读取完整流后才校验大小（low）。

## 九、前端专项：优化与改善建议汇总

按你的要求单独整理一份前端视角的问题清单（已在上文分类中出现，此处按前端维度重新归纳，方便前端同学对照处理）：

**架构/工程化**
- `web-antd`、`web-naive` 空壳脚手架建议删除或移出 workspace（3.4）
- 前端硬编码了本应由后端下发的权限元数据：隐藏路由权限码、菜单-权限映射表（3.5）
- 9 处重复的 `unwrap`/`unwrapPaged` 应抽取公共函数
- 资产表单与料件表单的图片上传/回显/竞态防护逻辑（约 100+ 行）应抽取为公共 composable

**Bug / 一致性**
- 资产表单编辑态未禁用部门/保管人选择，导致保存必被后端拒绝（用户体验差）
- 审批按钮缺少 `:disabled`，仅 `:loading` 不能阻止双击竞态
- `reject()` 缺少 `resolveNodeId()` 判空，与 `approve()` 不对称
- 资产查询过滤栏缺少已定义的部门筛选控件（死字段）
- 数量输入框应统一改用 `ElInputNumber` 做输入边界拦截
- 用户导入 / 项目导入弹窗的文件校验请求应加请求令牌防护，避免旧响应覆盖新选择

**性能**
- 逾期资产报表应改为服务端分页，与借用明细报表保持一致的实现方式
- 分类资产计数可考虑增量更新而非每次操作后整体重拉（数据规模增长后再评估）

**安全**
- JWT 存于 localStorage 且配合滑动续期放大 XSS 危害，建议评估迁移到 httpOnly Cookie 或至少增加"绝对生命周期"上限

**死代码清理**
- 已被注释的登录过期弹窗逻辑与仍保留的 `AuthenticationLoginExpiredModal` 组件引用
- 无引用的 `AssetCategoryDialog.vue`
