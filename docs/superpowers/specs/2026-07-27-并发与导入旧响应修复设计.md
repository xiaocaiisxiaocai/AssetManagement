# 并发与导入旧响应修复设计

## 背景与目标

本次修复聚焦两个已确认的边界问题：

1. `BaseDataService.UpdateDepartmentAsync` 在 MySQL `REPEATABLE-READ` 下，可能在锁定候选负责人之前由普通查询建立旧快照，使等待锁后的负责人唯一性检查看不到刚提交的占用。
2. 用户导入与测试项目导入只在选择新文件时推进请求代次；清空文件或关闭弹窗不会使在途校验失效，旧响应仍可能回填预览。

目标是在不新增数据库迁移、不改变现有接口契约的前提下关闭这两个窗口，并补充可重复执行的回归测试。

## 方案比较

### 方案一：调整事务读锁顺序并显式作废前端请求（采用）

- 后端在事务内首次一致性读取之前锁定候选负责人用户行，负责人占用检查在锁后执行。
- 必要时将候选负责人合法性与占用检查集中到锁后，避免后续维护重新引入旧快照。
- 前端在文件变更开始、清空文件、弹窗关闭时推进请求代次；只有最新代次可以写回预览和 loading 状态。

优点：改动小、无迁移、兼容现有数据和接口。缺点：唯一性仍由应用事务保证，不能抵御绕过应用直接写库。

### 方案二：增加数据库唯一约束

通过额外关系表或生成列约束“活动部门负责人唯一”。

优点：数据库提供最终一致性兜底。缺点：涉及 MySQL 5.7 条件唯一约束建模、迁移和存量数据清理，超出本次最小修复范围。

### 方案三：提高事务隔离级别并使用 AbortController

后端使用 `SERIALIZABLE`，前端主动取消旧 HTTP 请求。

优点：语义直接。缺点：后端锁范围和死锁风险明显增加；前端请求层改动面更大，收益低于复用现有代次守卫。

## 详细设计

### 后端负责人并发保护

- `CreateDepartmentAsync` 和 `UpdateDepartmentAsync` 保持相同锁顺序：开始事务 → 锁定候选负责人用户行 → 读取并校验部门状态 → 保存 → 提交。
- 对无需负责人唯一性校验的停用部门更新，不获取候选负责人锁。
- 保留现有业务异常口径：负责人已被其他活动部门使用时返回 `4094 / 负责人已负责其他部门`。
- 新增真实并发集成测试：两个活动部门同时更新为同一未占用负责人，最终必须恰好一个成功、一个被拒绝，数据库中只能有一个活动部门引用该负责人。

### 前端旧响应作废

- 每次文件输入变化时先调用 `invalidate()`，再清空旧预览；选择了有效文件后调用 `next()` 获取本次校验代次。
- 清空文件和关闭弹窗时调用 `invalidate()`，确保在途响应无法写回。
- 用户导入弹窗关闭路径与测试项目导入 `watch(visible)` 使用同一规则。
- 保持现有确认按钮条件：校验中、无文件、无预览或存在无效行时不可确认。

### 测试

- 后端：先增加并发更新测试并确认旧实现失败，再调整锁顺序使其通过；随后运行部门基础数据定向测试。
- 前端：增加针对“清空/关闭后旧代次失效”的测试，先确认调用方旧行为未覆盖，再实现失效逻辑；运行相关 Vitest。
- 完成后运行后端构建、完整后端测试、前端单元测试、`web-ele` 类型检查和 `pnpm check`。

## 非目标与回滚

- 不增加数据库迁移或唯一索引。
- 不修改部门、用户或导入接口的数据结构。
- 不引入新的请求取消基础设施。
- 如发生回归，可分别回滚后端锁顺序调整和前端调用方失效处理，两部分无数据迁移依赖。
